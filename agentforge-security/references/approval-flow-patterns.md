# Approval Flow Pattern Reference

> Sources: Claude Code [CC], Codex CLI [CX], Cline [CL], OpenCode [OC] approval flow implementations

## Pattern 1: Multi-Tier Decision Chain [CC]

Claude Code's approval flow is the most complex and complete implementation — an 11-layer decision chain evaluated serially by priority.

### canUseTool() Decision Flow

```
Tool invocation request
    ↓
1. Explicit Deny Rules
   → Match deny rule? → Reject (non-overridable)
    ↓
2. Safety Check Paths
   → Operating .git/.claude/configs? → Force prompt (bypass-immune)
    ↓
3. Content-Specific Rules
   → Parameter matching specific rules? (e.g., git push → prompt)
    ↓
4. Tool.checkPermissions()
   → Tool custom check passed?
    ↓
5. Permission Mode judgment
   → default: continue to next layer
   → acceptEdits: CWD edit auto-approved
   → auto: enter AI Classifier
   → bypassPermissions: nearly all pass (except bypass-immune)
    ↓
6. Allow Rules
   → Match allow rule? → Pass
    ↓
7. Safe Tool Allowlist
   → Read-only tools (Glob/Grep/Read)? → Pass in auto mode
    ↓
8. AI Classifier (auto mode only)
   → LLM judges if operation is safe
   → Fail-closed if unavailable
    ↓
9. Hook-Based Approval
   → Custom hook returns approve/reject?
    ↓
10. Denial Tracking
   → Consecutive rejections exceed limit? → Circuit break
    ↓
11. Fallthrough
   → ask (show UI to prompt user)
```

### Decision Result Types

```typescript
type PermissionDecision = {
  behavior: "allow" | "deny" | "ask";
  source: "explicit_deny" | "safety_check" | "content_rule"
        | "tool_check" | "permission_mode" | "allow_rule"
        | "safe_allowlist" | "ai_classifier" | "hook"
        | "denial_tracking" | "fallthrough";
  permanent: boolean;  // Whether to persist as a rule
};
```

### Audit Log

Each permission decision recorded:
```json
{
  "tool": "Bash",
  "input": "git push origin main",
  "decision": "ask",
  "source": "content_rule",
  "permanent": false,
  "permissionPromptStartTimeMs": 1712345678000,
  "permissionPromptDurationMs": 2340,
  "userDecision": "accept"
}
```

## Pattern 2: Policy Engine + Guardian AI [CX]

Codex CLI's approval flow has two stages: deterministic policy engine + probabilistic LLM evaluation.

### execpolicy Decision Flow

```
Agent generates shell command
    ↓
Stage 1: Starlark Policy Evaluation (deterministic)
    ↓
├── forbidden → Direct reject (no execution, no prompt)
├── allow → Direct execute (no user notification)
└── prompt → Enter stage 2
    ↓
Stage 2: Guardian AI Evaluation (optional)
    ↓
Guardian LLM receives:
  - User's original instruction
  - Command generated by Agent
  - Current filesystem context
    ↓
Evaluation dimensions:
  1. Does command match user intent?
  2. Any unexpected side effects?
  3. Is scope beyond what's necessary?
  4. Touching security boundaries?
    ↓
├── safe → Auto-execute
└── uncertain → Prompt user for confirmation
```

### The Value of Guardian AI

**Policy engine limitations**: Can only do pattern matching, no semantic understanding.

```python
# What the policy engine can handle:
prefix_rule(match="rm -rf /", decision="forbidden")  # Clearly dangerous

# What the policy engine cannot handle:
# "Delete all test files" → rm -rf tests/
# Policy engine doesn't know if this is reasonable — needs to understand user intent
```

Guardian AI fills the gap between the policy engine and user confirmation:
- Policy engine: handles **known patterns** (blacklist/whitelist)
- Guardian AI: handles **unknown patterns** (requiring semantic understanding)
- User confirmation: handles cases Guardian AI is also uncertain about

### Configuration

```toml
# codex.toml
[security]
approval_mode = "suggest"  # full-auto / suggest / locked-down

[guardian]
enabled = true
model = os.getenv("GUARDIAN_MODEL")  # Injected from env var; use nano/mini tier for cost control; confirm cheapest available model with WebFetch before using
```

## Pattern 3: AutoApprove Mode [CL]

Cline's approval flow focuses on user experience — reducing confirmation dialogs through declarative configuration.

### AutoApprove Configuration

```json
{
  "autoApprove": {
    "enabled": true,
    "actions": {
      "readFiles": true,       // Read file auto-approved
      "writeFiles": false,     // Write file requires confirmation
      "executeCommands": false, // Execute command requires confirmation
      "useMcp": false          // MCP tool requires confirmation
    },
    "paths": {
      "allow": [
        "src/**",
        "tests/**",
        "package.json"
      ],
      "deny": [
        ".env",
        "*.key",
        ".git/**"
      ]
    },
    "commands": {
      "allow": [
        "npm test",
        "npm run lint",
        "git status",
        "git diff"
      ]
    }
  }
}
```

### Decision Flow

```
Tool invocation request
    ↓
autoApprove.enabled?
├── false → Ask user for everything
└── true → Check action type
    ↓
actions[type] = true?
├── false → Ask user
└── true → Check path matching
    ↓
paths.deny match?
├── true → Ask user
└── false → paths.allow match?
    ├── true → Auto-approve
    └── false → Ask user
```

### Characteristics

- **Simple and intuitive**: Users don't need to understand complex policy languages
- **Coarse-grained**: Tool type + path pattern; no fine-grained command control
- **No Guardian AI**: No semantic understanding; pure pattern matching

## Pattern 4: Permission Channel [OC]

OpenCode's approval flow is the most minimalist — implements permission request/response via Go channel.

### Implementation

```go
type PermissionRequest struct {
    Tool     string
    Input    map[string]any
    Reason   string
}

type PermissionResponse struct {
    Granted  bool
    Remember bool  // Whether to remember this decision
}

// During Agent execution
func (a *Agent) executeTool(tool Tool, input map[string]any) {
    if !tool.IsReadOnly() {
        req := PermissionRequest{Tool: tool.Name(), Input: input}
        a.permissionChan <- req
        resp := <-a.responseChan

        if !resp.Granted {
            return  // Denied
        }
        if resp.Remember {
            a.allowedTools[tool.Name()] = true  // Remember
        }
    }
    tool.Run(ctx, input)
}
```

### TUI Dialog

```
┌──────────────────────────────────────┐
│  Permission Request                  │
│                                      │
│  Tool: Bash                          │
│  Command: git push origin main       │
│                                      │
│  [Allow]  [Allow Always]  [Deny]     │
└──────────────────────────────────────┘
```

### Characteristics

- **Minimal implementation**: Only channel + UI
- **No policy engine**: No declarative rules
- **No AI evaluation**: Pure human decision
- **Best for**: Small projects, personal tools

## Pattern Comparison

| Dimension | CC | CX | CL | OC |
|------|----|----|----|----|
| Decision layers | 11 | 2 (policy + Guardian) | 3 (action + path + cmd) | 1 (channel) |
| Policy language | JSON rules | Starlark DSL | JSON config | None |
| AI evaluation | Classifier | Guardian LLM | None | None |
| Circuit breaker | Yes | No | No | No |
| Remote killswitch | Yes | No | No | No |
| Multi-Agent forwarding | Yes | No | No | No |
| Audit log | Complete | Basic | None | None |
| Implementation complexity | High (~1500 lines) | Medium (~500 lines) | Low (~200 lines) | Extremely low (~50 lines) |

## Selection Guide

```
What type is your Agent?

├── Personal CLI tool
│   └── OC mode (channel + TUI) — simple enough
│
├── Developer tool (needs automation)
│   ├── Need custom policies?
│   │   └── CX mode (Starlark + Guardian AI)
│   └── Only need path control?
│       └── CL mode (AutoApprove config)
│
├── Commercial product (needs security compliance)
│   └── CC mode (complete decision chain + audit log)
│
└── Multi-Agent system
    └── CC mode + permission forwarding (required)
```

## Implementation Checklist

### Minimum Viable Approval Flow

- [ ] Distinguish read-only vs write tools
- [ ] Write tools prompt user by default
- [ ] User decision has allow / deny options
- [ ] Support "Allow Always" (remember decision)

### Production-Grade Approval Flow

- [ ] Declarative rules (deny/allow/ask)
- [ ] Rule priority: deny > allow > ask
- [ ] Fallthrough defaults to ask (never default to allow)
- [ ] Circuit breaker (pause after N consecutive rejections)
- [ ] Audit log (who / what / when / decision / source)
- [ ] Merge rules from multiple sources (org > project > user > session)

### Advanced Approval Flow

- [ ] AI Classifier / Guardian LLM
- [ ] Fail-closed when AI unavailable
- [ ] Remote killswitch
- [ ] Multi-Agent permission forwarding
- [ ] Temporary permissions (TTL)
- [ ] Hot policy updates (without restarting Agent)
