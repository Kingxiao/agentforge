# Agent 适用性判断矩阵

## 场景 → 方案映射

| 场景特征 | 推荐方案 | 理由 |
|---------|---------|------|
| 单输入→单输出，无状态 | LLM API 调用 | 最简单，成本最低 |
| 多轮对话，无副作用 | ChatBot（带历史） | 不需要工具系统的开销 |
| 固定步骤的工具调用 | Function Calling 管道 | 确定性高，易调试 |
| 动态多步推理 + 工具选择 | **Agent** | 需要循环和决策能力 |
| 长期个性化 + 主动触发 | **Agent + 记忆系统** | 需要跨会话状态 |

## 反信号（不该做 Agent 的场景）

1. **延迟敏感**：Agent 的多轮循环天然引入延迟。如果用户需要 < 1s 响应，Agent 不适合
2. **成本敏感**：Agent 每次执行消耗 5-50x 的 token（多轮 + 工具调用）。如果成本是关键约束，考虑管道方案
3. **确定性要求**：Agent 的路径是不确定的。如果需要 100% 可预测的行为，用传统工作流
4. **简单 CRUD**：如果核心操作是数据库 CRUD，不需要 AI 推理。传统 API 更可靠
5. **批量处理**：如果是大批量相同操作（如处理 10000 条记录），用批处理管道而非 Agent

## 成本估算参考

| Agent 类型 | 典型每次执行 token 数 | 参考成本 (Claude Sonnet) |
|-----------|---------------------|------------------------|
| 简单 Coding（改一个文件） | 10K-30K | $0.03-0.10 |
| 复杂 Coding（多文件重构） | 50K-200K | $0.15-0.60 |
| Research（搜索 + 综合） | 20K-80K | $0.06-0.24 |
| Data Analysis | 15K-50K | $0.05-0.15 |
| Workflow 编排 | 30K-100K | $0.09-0.30 |

注：以上为 Sonnet 级模型估算。Opus 级约 5x，Haiku 级约 0.2x。
