# 6 条自动决策原则详解

> 来源：gstack-autoplan 决策框架，适配 Agent 构建场景

## 原则 1：完整性优先

**规则**：覆盖全部边缘情况，不留"以后再补"的缺口。

**正例**：
- 工具接口定义了 `isReadOnly()`、`isExpensive()`、`needsConfirmation()` 等全部语义方法
- 安全模型覆盖了从工具级到容器级的 6 层
- 错误处理覆盖了 timeout、rate limit、auth failure 等全部场景

**反例**：
- "先实现核心功能，错误处理以后加" → 永远不会加
- "先支持一个 Provider，多 Provider 以后抽象" → 到时候重构成本 10x

**边界**：完整性不等于过度设计。如果某个边缘情况发生概率 < 1% 且影响可控，可以用日志记录而非完整处理。

## 原则 2：务实选择

**规则**：等效方案选更简洁的。复杂度是成本，不是特性。

**正例**：
- 文件记忆能满足需求时，不选块记忆
- `grep` 能完成的搜索，不建 AST 索引
- 单 Agent 能完成的任务，不用多 Agent

**反例**：
- 为了"架构优雅"引入消息队列，但实际只有一个 consumer
- 为了"可扩展性"用微服务，但只有一个服务

**边界**：务实不等于偷懒。如果简洁方案的扩展成本明显高于稍复杂方案的初始成本，选后者。判断标准：6 个月内是否大概率需要扩展。

## 原则 3：DRY（拒绝重复）

**规则**：同一信息只在一处定义。

**正例**：
- API endpoint 只在 `.env` / 配置文件中定义，代码引用配置
- 工具 schema 从代码自动生成，不手写 JSON
- 错误消息定义在一处，各模块引用

**反例**：
- 测试文件中硬编码 API endpoint（与配置文件重复）
- 多个文件中各自定义 `MAX_RETRIES = 3`

**边界**：3 行以内的简单逻辑，即使相似，不强制抽取。过度 DRY 比适度重复更糟——抽象本身也是成本。

## 原则 4：显式优于隐式

**规则**：每个决策都有可追溯的理由。

**正例**：
- 架构文档记录"选择 Async Generator 因为需要流式输出 + TS 生态"
- 安全决策记录"选择 OS 级沙箱因为 Agent 执行不可信代码"
- 跳过某个 Phase 时记录原因

**反例**：
- "用 Rust 因为 Rust 好" → 不是理由
- "默认配置就行" → 默认不是理由，需要说明为什么默认值合适

**边界**：机械决策（文件格式、import 风格）不需要长理由，一句话够了。品味决策需要理由。用户挑战需要完整分析。

## 原则 5：行动偏好

**规则**：默认推进而非等待。信息不足时，列出判断 → 提出方案 → 标注不确定性。

**正例**：
- Provider 方案未定时："暂定 Anthropic Claude 为主 Provider（因为 Agent 特化最好），后续可调整"
- 不确定用户需不需要多 Agent："建议跳过 Phase 7，如果后续需要再补"

**反例**：
- "请先确认 Provider 方案再继续" → 如果 Provider 选择不影响 Phase 2 的工具设计，应该继续
- "请确认是否需要 XXX 功能" → 如果答案不影响当前 Phase，不应阻塞

**边界**：涉及安全、成本、不可逆操作时，不能"先推进再调整"。安全相关的不确定性必须阻塞。

## 原则 6：安全保守

**规则**：权限/沙箱相关决策选更严格的选项。

**正例**：
- 不确定子 Agent 是否需要文件写入 → 默认禁止
- 不确定是否需要 OS 级沙箱 → 默认启用
- 不确定 API key 是否需要加密存储 → 默认加密

**反例**：
- "先不加权限控制，等出问题再说"
- "测试环境不需要安全检查"（测试环境的安全漏洞会被复制到生产）

**边界**：安全保守不等于安全偏执。如果 Agent 只读本地文件且不联网，不需要容器级隔离。安全措施应该与威胁模型匹配。

## 决策分类判断流程

```
遇到决策分叉
    ↓
该决策是否有唯一最优解？
├─ 是 → 机械决策 → 自动处理
└─ 否 ↓

该决策是否影响产品方向/用户体验/商业模式？
├─ 是 → 用户挑战 → 必须人工
└─ 否 ↓

该决策是否基于可能错误的假设？
├─ 是 → 前提假设 → 必须人工确认
└─ 否 → 品味决策 → 自动处理 + 记录理由
```

## 自动处理的输出格式

```markdown
### 自动决策：[决策名称]
- **类型**：机械 / 品味
- **选择**：[选定方案]
- **理由**：[一句话]
- **原则**：[适用的决策原则编号]
- **可逆性**：高 / 中 / 低
```

## 人工介入的提问格式

```markdown
### 需要你的决定：[决策名称]
- **类型**：用户挑战 / 前提假设
- **背景**：[为什么需要决定]
- **选项**：
  A. [方案 A] — [优劣]
  B. [方案 B] — [优劣]
- **我的倾向**：[如果有]
- **影响范围**：[这个决定会影响哪些后续 Phase]
```
